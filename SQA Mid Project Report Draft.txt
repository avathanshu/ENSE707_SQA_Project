1. Problem Definition and Approval

In November 2025, Shopify — the e-commerce platform underpinning millions of independent online stores — experienced a significant outage during Cyber Monday peak trading, leaving merchants unable to access checkout, cart, and inventory tools during the highest-revenue shopping event of the year. This incident is not an isolated case: e-commerce systems across the industry regularly perform acceptably under everyday load yet fail, slow down, or become unresponsive once concurrent demand spikes beyond the conditions exercised during development and pre-release testing.

This is fundamentally a software quality assurance problem rather than a functional-correctness problem. The affected systems typically satisfy their functional requirements under normal conditions, but their non-functional quality attributes — particularly performance, reliability, and scalability — are inadequately verified against realistic peak-load and failure conditions before release (Siddique, 2026a). The common industry mitigation, fixed-threshold monitoring, only catches degradation once it crosses a pre-defined limit; it does not learn what "normal" response-time behaviour looks like from historical operation, so subtler anomalies and gradual build-over-build regressions can pass undetected until a customer-facing failure occurs.

Several distinct software quality issues sit inside this one incident, and separating them clarifies what the project actually needs to measure. The first is a performance-efficiency issue: response time and throughput degrade as concurrency rises, and the point at which this happens is rarely known precisely because it is expensive to reproduce realistic peak-load conditions before release. The second is a reliability issue: a system can look reliable in isolation while still failing once a dependent service (payment, inventory, or notification) slows down under the same load, so reliability has to be assessed as a property of the whole request path, not a single component. The third is a monitoring and evidence issue rather than a coding issue: many teams only compare live metrics against a single fixed number, so a system that is degrading gradually, release after release, never crosses the alarm threshold until it is already too late. Framing the problem this way is what motivates the project's specific technical choices — load-profile variety, fault injection, a learned baseline, and cross-build regression tracking — rather than treating "the system was slow" as one undifferentiated failure.

The stakeholders affected by this problem span the e-commerce supply chain: platform engineering and QA teams responsible for capacity planning and release sign-off, merchants who depend on platform availability for revenue, and end customers attempting to complete purchases during high-demand periods. The problem is well suited to a one-semester Software Quality Assurance project because it can be reproduced and demonstrated entirely offline using a small, self-built sample API modelled on a specific, well-documented target (Shopify's checkout, cart, and inventory functions) rather than a generic e-commerce concept, keeping the scope concrete, testable, and achievable within the available time. Splitting the work into three independently ownable modules — target system and load generation, ML.NET anomaly detection, and regression tracking with reporting — gives each of the three team members a demoable, separately gradable component while still contributing to one coherent quality problem.

2. Requirements and Quality Analysis

2.1 How the Requirements Were Created

Requirements were derived in two steps. First, the problem statement in Section 1 was used to identify the high-level stakeholder needs (avoid peak-load failure, detect regressions early, give the team visibility of quality trends). Second, these needs were tested against a structured set of client-style questions (Appendix A) that specifically probed vague terms such as "fast", "reliable", and "peak load", following the guidance that vague words are prompts for clarification rather than requirements in themselves (Siddique, 2026a). Each requirement was then written, or rewritten, using the testable-requirement pattern: "Under [conditions], the system shall perform [observable behaviour], producing [expected result], within [threshold or tolerance]" (Siddique, 2026a), so that two independent reviewers could reach the same pass/fail conclusion from a test.

2.3 Requirements Quality Analysis

Each requirement was reviewed against the verification checklist of clarity, completeness, consistency, correctness, feasibility, and testability (Siddique, 2026a). For example, the initial idea for the performance requirement — "the system should respond quickly under load" — fails verification because "quickly" and "under load" have no agreed measurement context. It was rewritten as: "Under a steady-ramp load profile of N concurrent simulated users, the system shall flag an SLA breach whenever p95 response latency exceeds the configured threshold, measured over the run duration." This version is atomic, specifies the trigger condition, the observable behaviour, and the evaluation point, and can be judged pass or fail by any reviewer without relying on personal opinion.

An example acceptance criterion, written in Given-When-Then form for the regression-flagging requirement, is:

GIVEN a new build's load-test results have been persisted to the regression store

AND the previous three builds' results for the same test profile are available

WHEN the new build's mean response latency exceeds the historical baseline by more than the configured regression margin

THEN the dashboard shall mark the build as a regression and record it in the exportable QA report.

The requirements were also reviewed as a set, not only sentence by sentence, since two individually clear requirements can still conflict once combined (Siddique, 2026a). For example, the fixed-threshold baseline requirement and the ML.NET anomaly-detection requirement could be read as competing definitions of "abnormal" unless the requirement set makes explicit that the baseline is a comparison benchmark, not the system's actual detection mechanism; the requirement wording in Table 1 was checked to make sure this relationship, and not just each individual statement, was unambiguous.

The relevant software quality attributes identified for this project, mapped loosely to ISO/IEC 25010 categories discussed in Week 2 (Siddique, 2026b), are performance efficiency (response-time behaviour under load), reliability (correct anomaly and regression detection, no false SLA confirmations), maintainability (documented ML.NET feature engineering and model limitations so the model can be retrained), and usability (a dashboard that surfaces breach, anomaly, and regression status without requiring the viewer to read raw log files).

3. Proposed Solution and Initial Prototype

The proposed solution is a self-contained C# tool that load-tests the team's sample API, measures response-time behaviour under increasing concurrent load, and flags performance breaches before they would reach production. Unlike a simple fixed-threshold checker, it uses ML.NET to learn what "normal" response-time behaviour looks like from historical test runs, allowing it to flag abnormal degradation even when a hard-coded limit is not crossed, and it persists results across builds so that gradual, build-over-build regressions — the kind of rigid, insufficient capacity planning behind the Shopify incident — are also visible rather than only within-run anomalies.

The work is split into three independently ownable modules, each with its own functional requirements, so that contribution is separable and verifiable through individual GitHub commit history. Table 2 summarises ownership and scope.

  P1 – Target System & Load Generation   Avathanshu Bhat   Sample e-commerce API (checkout, cart, inventory) built and controlled by the team; C# load generator that ramps concurrent users across steady-ramp, spike, and soak/endurance profiles; records latency, error rate, and throughput; configurable fault-injection module.

  P2 – ML.NET Anomaly Detection          Quentin Masoe     Feature engineering from historical load-test run data; trains and evaluates an ML.NET anomaly model; benchmarks it against a naive fixed-threshold baseline with a precision/recall comparison; documents model limitations.

A GUI is appropriate for this project because the P3 component is a reporting and decision-support dashboard: it needs to present live metrics, breach/anomaly flags, and historical trend charts to a viewer making a release-readiness judgement, which matches the Assessment 1 guidance that a GUI is expected where the solution involves reporting, dashboards, or end-user decision support. The dashboard's colour palette and layout are intentionally kept close to Shopify's own admin-console styling, since the sample API it reports on is deliberately modelled on Shopify's checkout/cart/inventory domain rather than a generic storefront, which keeps the prototype's visual language consistent with the real-world system that motivated the problem.

4. AI-Assisted Development Using GitHub Copilot

GitHub Copilot is being used across all three modules to support boilerplate coding, unit-test scaffolding, and documentation, in line with the Assessment 1 terms encouraging AI-assisted development provided all outputs are reviewed, validated, and understood by the student who submits them. Each member is keeping a short log of representative prompts and the suggestions accepted, modified, or rejected, so that AI use can be evidenced rather than merely claimed.

4.1 Representative Example (P3 – Regression Tracking)

The eleven test cases in Section 6 were also first drafted with Copilot rather than written from scratch, in line with the clarified task instructions. Copilot was given each requirement's acceptance criterion as a prompt and asked to propose test steps, inputs, and an expected result; this produced a reasonable first pass for straightforward cases such as TC-01 and TC-02, but consistently under-specified the concurrency-sensitive cases (TC-04 and TC-07), where its first draft described a single sequential request rather than the overlapping or multi-build sequence the requirement actually depends on. Every generated test case was therefore checked against the corresponding requirement and acceptance criterion before being accepted into Table 3, and the correction made to each case is treated as evidence of human validation rather than a failure of the tool.

For example, when implementing the build-over-build comparison logic, Copilot was prompted with a comment describing the intended behaviour ("compare the new build's mean latency against the mean of the previous three builds for the same profile and return a regression flag if it exceeds the configured margin") and produced an initial method implementation. On review, the generated code compared the new build only against the immediately previous build rather than the three-build rolling mean specified in the prompt, and it did not guard against a division-by-zero when fewer than three prior builds existed. Both issues were corrected by hand, and a unit test was added to lock in the intended three-build rolling-mean behaviour before the fix was accepted.

4.2 Limitations and Reflection

Across the examples reviewed so far, the recurring risks with Copilot-generated code are: (1) plausible-looking logic that silently narrows the scope of what was asked (e.g. comparing against one prior build instead of a rolling window); (2) missing edge-case handling, particularly around empty or small historical datasets; and (3) confident-sounding comments that do not match what the generated code actually does, which can mislead a reviewer who skims rather than tests. These risks mean Copilot is most useful for reducing the time spent on boilerplate and repetitive test scaffolding, while threshold values, statistical comparisons, and anomaly-classification logic still require the team to write and defend the test cases independently, as also required for Task 6 of this assessment.

5.2 Test Levels and Testing Approach

The strategy uses the four core test levels — unit, integration, system, and acceptance (Siddique, 2026c) — mapped to the project as follows:

-   Unit testing (MSTest): isolated logic such as SLA-breach threshold checks, the ML.NET feature-engineering functions, and the build-over-build comparison logic, each with dependencies mocked or replaced.

-   Integration testing: the load generator against the sample API under a running load profile; the anomaly detector against a persisted batch of historical run data; the regression store against the dashboard's data-access layer.

-   System testing: an end-to-end run from load-test execution, through anomaly/regression detection, to dashboard display and QA-report export.

-   Acceptance-level checks: manual review of the exported QA report and dashboard views against the acceptance criteria defined in Section 2.3.

Functional testing uses black-box techniques — equivalence partitioning and boundary-value analysis around capacity, concurrency, and latency thresholds — designed directly from the acceptance criteria, since acceptance criteria are a strong test basis even before a final test suite exists (Siddique, 2026c). Non-functional testing focuses on performance (response-time behaviour under the three load profiles) and reliability (the anomaly detector's precision/recall against the fixed-threshold baseline on identical historical data), reported as the primary non-functional evidence for this phase.

5.3 Entry and Exit Criteria

  -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  Criteria             Description
  -------------------- ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  Entry criteria       A buildable version of the relevant module is available in the repository; test data (synthetic historical run records) is prepared; the local/offline test environment is configured; no blocking integration failures between the module under test and its immediate dependencies.

  Exit criteria        All planned unit tests for the module pass; no unresolved high-severity defects in the functionality under test; the anomaly detector's precision/recall has been recorded against the fixed-threshold baseline (even if not yet meeting a target); results are logged in the traceability matrix.

Exit criteria express the evidence and risk tolerance the team has agreed for this phase; they do not claim that no defects remain (Siddique, 2026d).

-   Synthetic historical load-test data generated by the team (rather than production data) to train and evaluate the ML.NET model and to construct build-over-build regression scenarios.

-   WinForms/Blazor for the dashboard, exercised through manual system-level walkthroughs at this phase.
